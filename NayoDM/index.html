The challenge

IFS data migration is where implementations lose time.

IFS data migrations involve intricate setups, require specialist knowledge and present validation challenges at every entity. Without the right tooling and visibility, these projects absorb weeks that were budgeted for configuration and testing.

Intricate setups

Each migration entity carries its own key structure, dependencies and mandatory attributes. Loading them in the wrong order, or without the reference data in place, fails deep in the run.

cost: repeated load attempts

Specialist knowledge

Getting data into IFS reliably means knowing the projections, the LU model and the rules IFS applies on import — knowledge that usually sits with one or two people on the project.

cost: a single point of dependency

Validation blind spots

Spreadsheets accept anything. Errors surface only once records reach IFS, in volumes that are slow to unpick and expensive to reload.

cost: rework late in the plan

Pre-flight validation

Two checks before anything reaches IFS.

IFS data migrations involve intricate setups, specialist knowledge and validation that is easy to get wrong. Without the right tooling and visibility, teams find the bad rows after the load — and the project pays for it in delays and cost.

NayoDM runs two passes before a single record moves. The first checks every row against the target's own rules. The second is the one that catches most real migration failures: it collects the values your data refers to — country codes, delivery terms, units, customer groups — and confirms each one already exists in IFS.

  • Pass 1 — row rules — required values, formats, lengths and types, checked on every record, with warnings kept separate from errors.
  • Pass 2 — basic data — every distinct referenced value is looked up in IFS, so a missing delivery term or customer group is found before the load, not during it.
  • A list you can act on — the exact values still to be created in IFS, named and counted, rather than a wall of rejected rows.
  • Grouped by field — results counted per field, so you fix a rule once instead of chasing individual records.

Mapping & transformation

One target attribute, several source columns, real rules.

Real migrations are rarely one-to-one. A single IFS attribute is often assembled from several legacy columns, resolved through a cross-reference table, reformatted, defaulted where the source is empty, or left for IFS to derive at import time. NayoDM holds all of that in the mapping itself, so the rule travels with the project and can be reviewed, corrected and repeated in the next environment.

  • Cross-reference lookups — resolve legacy codes against a reference sheet held with the project; unmatched values are reported by pre-flight rather than loaded blind.
  • Composite and conditional values — concatenate, pad, default and branch on the source row, evaluated per record.
  • Format normalisation — legacy date and numeric formats converted to the target's expected form, with failures surfaced by field.
  • IFS-resolved attributes — values IFS derives on import are marked in the mapping and reported as warnings rather than failing the run.

Documents

Drawings, specifications and certificates, attached to the right object.

Point NayoDM at a document folder and its manifest, and the files are migrated as IFS documents — the class and format validated first, the document created, the file uploaded, and the result attached to the business object the manifest names.

  • Manifest-driven — class, number, sheet, revision, type, title and file name are declared per document and validated before anything is uploaded.
  • Attached on creation — each document is linked to its logical unit and key reference, so it lands against the part, order or object it belongs to.
  • Numbering handled — take the number from the manifest, or let IFS allocate it from the document class counter.
  • Per-row run log — every file records an outcome against its document number, exportable for handover and audit.

IAM client migration

Move integration access with the data.

Interfaces need their access clients in place before the first message flows. NayoDM creates them from a single configuration sheet — identifier, description, service user and enabled state — and records the outcome of every row, so access configuration is reproducible across every environment in the landscape.

  • Bulk creation — one configuration sheet per environment, applied in a single run.
  • Service users handled — optionally ensure the service user exists and is linked as the client's identity.
  • Enabled state respected — clients are created active or disabled exactly as declared.
  • Result log per row — created, skipped and failed outcomes exported for the security team's records.

Workflow engine

Fixing 3 412 order lines without touching them one by one.

The load is rarely the end of it. Orders arrive carrying delivery terms the old system used and IFS does not recognise; balances need adjusting after the count; a batch of records has to be released once the data behind it is in place. Doing that by hand means someone in a screen for a week — and no record of what was changed.

A workflow does it as one job: select the affected records, take a backup, apply the rule, and check the result — with every record's outcome written down and the whole run reversible if the rule was wrong.

  • Correct values after a load
    Legacy codes translated to their IFS equivalent across every affected line, with unmatched values held for review instead of guessed.
    after each load
  • Release transactional records in bulk
    Move orders, requisitions or shop orders to their live state once the master data behind them has been checked.
    before go-live
  • Reprocess what failed
    Take the records a load rejected, apply the fix, and resubmit them — without re-running the whole import.
    any run
  • Adjust balances and dates
    Apply a correction to inventory or scheduling data when the count and the extract disagree.
    before go-live
  • Reversible — the affected records are captured before anything is written, so a run can be undone.
  • Accountable — every record's outcome is recorded: updated, held for review, or failed, with the reason.
  • Repeatable — the same job runs again in test, then in production, without being rebuilt.
  • Unattended — long jobs run in the background while the team carries on with the rest of the migration.

Built for real volumes

Large loads finish, and you can prove it.

Inventory balances, order lines and part catalogues run into the hundreds of thousands of records. NayoDM takes them a batch at a time and saves its position as it goes, so a large load is something the team starts and checks on rather than sits and watches.

  • Nothing is loaded whole — records are read a batch at a time, so the size of the file or the table does not decide whether the run survives.
  • It saves as it goes — the load is written in chunks, and a run that stops or is interrupted continues from the last saved point instead of starting again.
  • You can see where it is — records loaded, records remaining, current rate and time left, updated while it runs.
  • Sized to the environment — how much is read and written at a time is a setting, so a modest test system and a production environment can both be loaded sensibly.
  • Every run is written down — each record's outcome is recorded for handover and audit.
