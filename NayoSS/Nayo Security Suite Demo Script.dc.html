Opening — The Problem

For most IFS customers, security is the hardest part of moving from an older IFS version to IFS Cloud. Projection grants and permission set handling rarely carry over cleanly, and remapping them by hand costs weeks of effort. Beyond migration, IFS Cloud gives no consolidated view of what's actually granted, and routine user administration such as duplicating a user's access is largely manual. Nayo Security Suite offers a fast, straightforward way to migrate, review, and manage security across all of these.

Product Overview

Nayo Security Suite is an advanced solution designed to simplify and streamline security data management across IFS environments. It enables seamless security migration from legacy systems — including IFS IEE — to IFS Cloud, and supports extracting, modifying, and re-importing security data within IFS Cloud. It also centralizes environment connectivity and user management — permission sets, companies, sites, user groups, and one-step user duplication — with segregation of duties coming soon.

Key Features

IFS Environment MaintenanceAdd, edit, and test connections to IFS IEE and IFS Cloud environments.
Security MigrationSeamless uplift and migration of security data from IFS IEE and older IFS versions into IFS Cloud, preserving existing roles, permissions, and security structures.
IFS Cloud Security ManagementExtract existing IFS Cloud security configuration, then review and update it.
User ManagementCentralized management of users across connected environments.

Scene 1 — Overview

Before we dive in, here's a quick recap of what Nayo Security Suite does. It brings together IFS environment management, security migration from IFS IEE to IFS Cloud, IFS Cloud security export and import, user management, and, coming next, segregation of duties — all in one tool, so security data across your IFS environments is easy to manage, review, and update. Let's walk through each of these, starting with the home page.

Scene 2 — Home Page

This is the Nayo Security Suite home page. It shows shortcuts to each feature — Permission Set Migration, Export/Import, Users, and IFS Environments. On the right, it lists the environments already configured. Let's go to IFS Environments, where environments are maintained.

Scene 3 — IFS Environments

Here you can see the environments already added, and you can edit or delete any of them. The "Add IFS Environment" button lets you add a new one. The table lists each environment's name and type, so you can filter by either. Clicking "Add IFS Environment" opens a modal with the fields needed to configure and connect the environment. Today we support two environment types: IFS IEE and IFS Cloud.

For IFS IEE, you'll provide the environment name, username, password, database host, port, database or service name, and an optional description. Once the required fields are filled in, press "Create Environment" to create it. You can also verify connectivity at any time with the "Test Connection" button, which reports success or failure.

For IFS Cloud, the configuration is different: base URL, client ID, client secret, and the well-known configuration endpoint. As with IEE, you can test the connection and create the environment using the same two buttons.

Adding an IFS IEE Environment

Let's add an IFS IEE environment. I'll name it "IFS IEE APP," set the environment type to IFS IEE, and provide the username and password. For database configuration, I'll provide the host, port, and database or service name. Once all the required details are in, I'll press "Test Connection" — connection succeeds — then press "Create Environment." The new environment now appears in the list.

Adding an IFS Cloud Environment

Let's add an IFS Cloud environment too. Before doing that, there are a few prerequisites to complete on the IFS Cloud side — creating an IAM client and granting the required permission sets to its service account user. We won't walk through those here; the full setup steps are covered in the setup document that comes with the tool.

With the prerequisites in place, let's add the IFS Cloud environment. I'll name it "IFS DEMO APP," provide the base URL of the Cloud environment, and enter the client ID and secret from the IAM client, along with the well-known configuration endpoint.

There's also an SSL certificate verification toggle — switch it off when the environment doesn't have proper certificate signing, or uses a self-signed certificate. Then I'll test the connection — it succeeds, confirming all the details match — and create the environment. Now both the newly added IEE and Cloud environments are listed.

Scene 4 — Permission Set Migration

Now let's look at Permission Set Migration. Here's the problem it solves: when clients migrate from an older IFS version to IFS Cloud, their custom permission sets carry over, but the projection grants don't. Nayo Security Suite maps the older version's presentation objects to the equivalent projections in the newer version — using AI matching, descriptions, labels, and a pre-identified mapping file — then grants the most accurate matches to the selected permission sets.

The migration flow has four steps: Define Environments, Select Permission Sets, Mapping Preview, and Grant Projections.

Step 1 — Define Environments. Select a source and a target environment. The source must be an IFS IEE environment; the target is the IFS Cloud environment. Once selected, the tool shows the connection status for each independently. When both connections succeed, you can proceed to the next step.

Step 2 — Select Permission Sets. This step lists all custom permission sets found in the source IFS IEE environment. You can select all of them, or specific ones — for this demo, I'll select Nayo_Purchase and Nayo_Sales. Once selected, the table footer confirms the selection: two permission sets covering 366 presentation object IDs. Those IDs are what we'll map to IFS Cloud projections in the next step.

Step 3 — Mapping Preview. Once mapping completes, the preview shows each presentation object ID and its mapped projection, along with the IEE name, Cloud name, mapping method used, and the component it belongs to.

Before moving to the final step, let's check the source environment — IFS Applications 10 — to see how the two selected permission sets currently look. NAYO_SALES has a number of object grants, and so does NAYO_PURCHASE.

Now let's check IFS Cloud before running the migration. Both custom permission sets exist there already, but neither has any projections granted yet.

Back in Nayo Security Suite, the mapping preview shows each presentation object matched to a projection, along with the method used — Description, AI, Manual, or Label. You can also export the mapping summary to Excel; the export includes three sheets: Unmatched IEE, Unmatched IFS Cloud, and Matched IFS IEE vs. IFS Cloud.

Step 4 — Grant Projections. This step lists the two selected permission sets, each with the projections mapped by the tool underneath. You can grant them individually, or all at once — let's grant both together using the "Grant Permission" button at the bottom of the table. A confirmation dialog appears, asking what access level to apply to partially granted IEE objects: Full or Read-Only. We'll choose Full.

The grant runs with a live progress bar and completes successfully. You can review the "Grant Activity Log" for a detailed record of everything that happened during the process, and download it if needed.

To confirm the grant succeeded, let's return to the IFS Cloud environment and refresh. NAYO_SALES and NAYO_PURCHASE now both have their projections granted with full access.

Scene 5 — Export / Import

IFS Cloud doesn't offer a clear, consolidated view of security details. Nayo Security Suite solves this by exporting selected permission sets — organized by IFS Cloud navigator items — into a spreadsheet that's much easier to read.

Let's walk through an export. First, choose an environment. Once you select the IFS Cloud environment, the right panel shows end-user permission sets by default; check "Functional Role" to include functional permission sets as well. On the left, you'll see the root-level IFS Cloud navigator items — select all, or specific ones. For this demo, I'll select the Nayo_Purchase and Nayo_Sales permission sets, with the Procurement and Sales navigator items.

Pressing "Proceed Export" opens a modal with three options: Export Empty Spreadsheet, Include Actions (checked by default), and Include Custom Projections Not Registered to the Navigator. Export Empty Spreadsheet starts a fresh export with no existing grants populated. Include Actions determines whether each projection's entity actions are included alongside the projection itself. Include Custom Projections covers any custom projections that aren't registered to a navigator item.

For this demo, I'll uncheck Include Actions and export without them by pressing "Start." Once export completes, you're prompted for a destination folder and file name. Let's open the exported spreadsheet.

The spreadsheet lists the selected navigator root items down the rows and the selected permission sets across the columns. Each permission set has three sub-columns: None, View, and Edit — representing no access, read-only, and full access respectively.

Expanding a navigator item reveals its sub-items, and expanding one of those — Order, for example — reveals the individual pages and their associated projections. In row 48, "Order" shows an X marked across all three columns under NAYO_PURCHASE, indicating that access across Read-Only, Full, and None is mixed within that group — so you know at a glance there's variation without expanding further. Drilling in: PurchaseOrdersHandling has full access, PurchaseOrderChargesHandling has read-only access, and QuickPurchaseOrderRegisterHandling has no access granted.

You can also update access levels directly in the spreadsheet. Let's try CustomerOrderHandling: I'll enter "M" in the View column for NAYO_PURCHASE, and "M" in the View column for PurchaseQuotationHandling under NAYO_SALES. First, back in IFS Cloud, let's confirm neither grant currently exists — there's no CustomerOrderHandling grant for NAYO_PURCHASE, and no PurchaseQuotationHandling grant for NAYO_SALES.

Back in Nayo Security Suite, switch to Import. Select the Cloud environment to update, then choose the modified spreadsheet. You can specify the "update character" the tool should read during import — "M" by default — and use any letter except "X." There's also an option to create a new permission set, which I'll cover shortly.

Pressing "Proceed Import" prompts a confirmation dialog. Once confirmed, the import runs with a live progress bar and log, and completes successfully. Back in IFS Cloud, after refreshing: NAYO_SALES now has PurchaseQuotationHandling with read-only access, and NAYO_PURCHASE now has CustomerOrderHandling with read-only access.

Back in the tool, the live log shows every activity that occurred during the import.

Creating a New Permission Set from the Spreadsheet

To create a new permission set using the exported spreadsheet, start by copying an existing permission set's column and clearing its existing grant data. Rename the copied column to the new permission set's name. The suffix in parentheses indicates the role type — "(E)" for an end-user role, or "(F)" for a functional role. For this demo, I'll grant full access to several projections across both Sales and Procurement by entering "M" in the Edit column.

Currently, NAYO_SALES_SPV doesn't exist in IFS Cloud. Let's import the modified spreadsheet, making sure "Create New Permission Set" is checked — without it, the new permission set won't be created. Pressing "Proceed Import" opens a confirmation dialog; once confirmed, the tool reads the modified spreadsheet with live logs and creates the new permission set. After refreshing the IFS Cloud page, NAYO_SALES_SPV now exists, with the full-access projection grants we assigned.

Scene 6 — User Management

The User Management feature lets you grant and revoke permission sets, companies and sites, and user group assignments for individual users — with a clear summary view of everything a user has been granted.

This addresses a significant pain point in IFS Cloud: when you duplicate an existing user, Cloud doesn't carry over that user's permission sets, companies, sites, or user group grants — and it doesn't create sites per user either. Nayo Security Suite solves both problems directly. For example, say User A leaves the company and User B is taking over their role. With this feature, you can simply duplicate User A with all their relevant permissions — so User B doesn't need to be set up from scratch.

First, select the IFS Cloud environment. Once selected, the tool displays all users currently in that environment — I'll search for a test user for this demo. Selecting a user shows their details on the right, across four tabs: Permission Sets, Companies & Sites, User Groups, and Summary.

The Permission Sets tab lists End User and Functional permission sets; the ones already granted to the user are highlighted in green. Grant or revoke by checking or unchecking the box preceding each permission set name. Functional role checkboxes are disabled, since functional roles can't be granted directly to a user.

The Companies & Sites tab groups sites under their parent company — companies at the root level, with their sites listed underneath. The User Groups tab lists all user groups in the Cloud environment, with the ones already assigned to the user highlighted in green.

The Summary tab gives a consolidated view of everything: direct and indirect permission set grants, companies and sites, and user groups.

Granting and Revoking

Let's grant something to this user. Alongside the permission sets already highlighted in green, I'll add the NAYOSS_ADMIN permission set. Checking it enables the Save and Discard buttons, and the counter panel shows "1 new." Pressing Discard would clear any newly checked items. The same approach applies to selecting a default company and site, and to user groups.

Pressing Save opens a confirmation modal summarizing the pending changes — in this case, one permission set grant. Confirming completes the grant successfully, and the Summary tab now shows NAYOSS_ADMIN as a new direct grant.

To verify in IFS Cloud: before the change, the user has two permission sets as direct grants; after reloading, NAYOSS_ADMIN now appears as a third. The "All Grants" tab confirms its grant type as Direct.

Revoking works the same way, in reverse.

Duplicating a User

Now let's duplicate this user. Press "Duplicate User" and provide a new identity for the duplicate — the directory ID can be changed or left matching the identity, and other properties can be adjusted as needed. Once the required fields are filled in, press "Create User" to complete the duplication. The newly created user appears with the same permission sets as the original.

Checking IFS Cloud after a reload confirms the new user, with matching permission sets, groups, and companies. The tool also creates a corresponding Person record. Looking at the user's sites, the tool has created sites per user — two sites plus a default site, mirroring the source user's setup exactly.

Scene 7 — Coming Next: Segregation of Duties

Before we wrap up, a look at what's coming next: Segregation of Duties. This feature will let you review conflicting permission sets across your IFS Cloud environment — identifying combinations of access that shouldn't sit with the same user or role. You'll be able to upload your own SoD ruleset, define which permission set and projection combinations are considered conflicts, and have the tool evaluate your environment against those rules. The result is a clear view of where SoD violations exist, so you can resolve them before they become audit findings.
